# 코드 리뷰 체크리스트 스킬

이 스킬은 이 프로젝트에서 "코드 리뷰"를 요청받았을 때 따르는 표준 절차다.
목표는 **근거 없는 지적을 줄이고, 실제로 문제가 되는 것만 정확한 위치와 함께 보고하는 것**이다.

## 0. 리뷰 대상 파악

인자(args)나 대화 맥락에서 리뷰 대상을 판단한다. 우선순위:

1. 사용자가 특정 파일/디렉터리/PR 번호/브랜치를 명시 → 그것을 대상으로 함
2. 명시가 없고 git 저장소인 경우:
   - `git diff` (unstaged) 와 `git diff --staged` 를 모두 확인
   - 둘 다 비어 있으면 `git log -1`의 최근 커밋 diff를 후보로 제시하고 사용자에게 범위를 확인
3. git 저장소가 아니거나 diff가 없으면, 사용자에게 리뷰할 파일/코드를 물어본다 (추측해서 임의 파일을 넘겨짚지 않는다)

리뷰 범위가 크면(여러 디렉터리, 대규모 diff) 먼저 변경된 파일 목록을 보여주고 우선순위(핵심 로직 > 설정/스타일 파일)를 정한 뒤 진행한다.

## 1. 컨텍스트 확보

- diff의 앞뒤 몇 줄만 보지 말고, **변경된 파일 전체**를 읽어서 주변 코드 스타일과 기존 패턴을 파악한다.
- 같은 프로젝트 내 유사 기능(같은 종류의 API 핸들러, 같은 종류의 컴포넌트 등)이 있으면 비교해서 "이 프로젝트에서의 관례"를 기준으로 삼는다.
- CLAUDE.md, README, 기존 테스트 코드가 있으면 프로젝트 컨벤션 파악에 활용한다.

## 2. 체크리스트

아래 카테고리를 순서대로 점검한다. 각 카테고리에서 발견한 것만 기록하고, 해당 사항이 없으면 넘어간다 (없는 것도 언급할 필요 없음 — 침묵이 곧 "문제 없음"이다).

### A. 정확성 / 로직 버그 (최우선)
- 조건문/반복문 경계 오류 (off-by-one, 부등호 방향)
- null/undefined/None 처리 누락으로 인한 런타임 에러 가능성
- 비동기 코드의 race condition, 처리되지 않은 Promise/await 누락
- 타입 불일치, 암묵적 형변환으로 인한 의도치 않은 동작
- 변경된 로직이 실제로 요구사항/함수명이 암시하는 동작과 일치하는지

### B. 보안
- 사용자 입력 검증 누락 (SQL/NoSQL injection, XSS, command injection, path traversal)
- 비밀키/토큰/자격증명 하드코딩 또는 로그 노출
- 인증/인가 체크 누락 (특히 새로 추가된 API 엔드포인트)
- 안전하지 않은 역직렬화, `eval`류 사용
- 의존성에 알려진 취약점이 있는 새 패키지 추가 여부

### C. 에러 처리 & 엣지 케이스
- 예외를 삼키기만 하고 로깅/처리하지 않는 빈 catch
- 외부 호출(네트워크, 파일, DB) 실패 시 처리 경로
- 빈 배열/빈 문자열/0/음수 등 경계값 처리
- 에러 메시지가 원인 파악에 충분한 정보를 담는지

### D. 성능 / 효율성
- 불필요하게 반복되는 연산 (루프 안의 DB 쿼리, 불필요한 재렌더링 등 N+1류 패턴)
- 큰 데이터 처리 시 메모리/시간 복잡도 문제
- 이미 있는 유틸/라이브러리 기능을 재구현하고 있지 않은지

### E. 가독성 / 유지보수성
- 이름만으로 의도가 드러나지 않는 변수/함수명
- 같은 로직의 중복 (추출 가능한 중복 코드)
- 지나치게 깊은 중첩, 너무 긴 함수 (관심사 분리 필요 여부)
- 매직 넘버/문자열을 상수화했는지
- 죽은 코드(사용되지 않는 변수/함수/import)

### F. 테스트
- 새 로직/버그 픽스에 대응하는 테스트가 있는지
- 기존 테스트를 깨뜨리지 않았는지 (가능하면 실행해서 확인)
- 테스트가 실제 동작이 아니라 구현 세부사항만 검증하고 있지 않은지

### G. 일관성
- 프로젝트의 기존 스타일(네이밍, 폴더 구조, 에러 처리 패턴)과 어긋나지 않는지
- 린터/포매터 설정이 있다면 그것을 위반하지 않는지

## 3. 검증 (false positive 줄이기)

발견한 각 항목에 대해 보고 전에 스스로 확인한다:
- 실제로 해당 코드 경로가 실행될 수 있는가? (죽은 코드/도달 불가능한 분기 지적 아님)
- 이미 상위/하위 레이어에서 처리되고 있는 문제는 아닌가?
- 프로젝트의 의도적인 설계 선택은 아닌가? (확신이 없으면 "확인 필요"로 표시하고 단정하지 않는다)

근거가 약한 지적은 버리거나, 확신도가 낮음을 명시한다. 지적 개수를 늘리는 것보다 정확도가 우선이다.

## 4. 보고 형식

- `ReportFindings` 도구가 사용 가능하면 그것으로 보고한다 (심각도 높은 순 정렬, 문제 없으면 빈 배열).
- 사용할 수 없다면 다음 마크다운 형식으로 직접 출력한다:

```
## 코드 리뷰 결과

### 🔴 Critical / Major
- **[파일:라인]** 한 줄 요약
  - 문제: 구체적인 실패 시나리오 (입력값 → 잘못된 결과/크래시)
  - 제안: 수정 방향 (필요시 코드 스니펫)

### 🟡 Minor
- ...

### 💬 Nit (선택적 제안, 스타일/취향)
- ...

발견 사항 없음: (있다면) "N번 카테고리는 문제 없음"
```

- 각 항목은 반드시 `file:line` 형태로 위치를 명시한다 (clickable 참조).
- 좋은 점(잘 처리된 부분)이 있다면 간단히 한 줄로 인정해도 되지만, 리뷰의 본체는 문제 지적이다.

## 5. `--fix` 옵션

사용자가 "고쳐줘", `--fix` 등을 함께 요청한 경우:
1. 먼저 위 형식대로 발견 사항을 보고한다.
2. Critical/Major 항목부터 실제 코드에 수정을 적용한다 (Edit 도구 사용).
3. 적용/보류 여부를 각 항목에 표시해서 다시 요약한다 (예: "적용함", "판단 필요해 보류").
4. 스타일 취향에 가까운 Nit은 사용자가 명시적으로 요청하지 않는 한 자동 적용하지 않는다.
